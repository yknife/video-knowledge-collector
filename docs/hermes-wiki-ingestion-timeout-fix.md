# Hermes Wiki 入库超时排查与修复

2026-09-25 的桌面日志显示，入库任务集中运行期间，VKC SQLite 连接池达到 `size 5 + overflow 10` 上限，随后媒体列表、任务列表等 API 在等待连接 30 秒后报 `sqlalchemy.exc.TimeoutError`。Electron 对普通 API 请求使用 15 秒空闲超时，因此先出现 `Timed out connecting to Hermes backend after 15000ms`。这条 Electron 文案也会用于等待响应超时，不能据此判断 TCP 连接失败；检查时后端、Worker 进程和本地监听端口仍存在。

桌面 VKC 事件订阅原先对**每一条** `job.progress` 都失效整个 `video-knowledge` 查询前缀，包括媒体、Wiki、任务、来源和设置。实际任务事件在一段三分钟窗口内包含 167 条进度事件；多任务集中入库会放大并发查询。现将事件合并到 750 毫秒窗口：进度仅刷新任务与任务事件，状态变化再刷新全局数据。连接池报错与该请求放大同时出现；现有日志无法单独证明它是连接池耗尽的唯一原因。

另有一项明确的入库失败：一份已经完成的分析在两个知识点的引用里重复列出同一个转录片段 ID。旧版来源冻结器将重复 ID 视为致命错误，相关 `WIKI_INGEST` 达到 3 次尝试后失败。修复后仍校验片段存在和准确时间范围，在不可变来源快照中保留原始分析，只在 Wiki 页面引用里按原顺序去重。

此外，有一项独立的 `WIKI_FUSE` 因模型未提交通过校验的变更集而失败。其来源视频页已先行持久提交，融合失败不会撤销该来源；审计中可见模型读取方向、来源及页面后提交了一次被拒绝的变更集。现有审计仅记录异常类型，无法从历史报告还原被拒绝的具体字段，因此不能把它归因于 SQLite 超时。可在任务中心单独重试该融合任务。

回归覆盖 20 条突发进度事件只产生一次任务刷新、状态变化产生一次全局刷新，以及重复引用的来源快照与页面引用。修复需要重启当前 Hermes Desktop 后端与 VKC Worker 才会由运行中的 Python/Node 进程加载；已有失败任务可在任务中心手动重试，重试会保留原任务审计并增加尝试预算。正在运行的融合任务是独立的持久任务，重启前应等其结束；本文的检查没有修改真实 Wiki 或任务状态。
